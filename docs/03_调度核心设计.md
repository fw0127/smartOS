# 03 调度核心设计

> 本篇只使用抽象术语(见 02 篇第 3 节),不涉及任何具体平台。

## 1. 核心决策一览

| 问题 | 决策 | 理由 |
|---|---|---|
| 抢占 vs 协作 | **协作式,运行到完成** | 单执行流、任务间无需加锁、行为可静态分析 |
| 任务形态 | **一次 `run` = 推进一步的非阻塞函数** | 与"状态机步进"写法天然契合 |
| 优先级 | **静态、唯一**,数值越小越高 | 构建期可排序,运行期无需比较 |
| 就绪查找 | **就绪位图 + 最低置位查找**,常数时间 | 选择开销与任务数无关(D1) |
| 派发粒度 | **每次派发一个任务,然后重新评估** | 高优先级任务的等待上限 = 最长单步时间 |
| `AGAIN` 公平性 | **连续 N 次后让出一次** | 防止持续工作的任务饿死低优先级任务(D3) |
| 时间 | **抽象单调计数 + 回绕安全比较** | 不依赖时钟来源、不需要周期性中断 |
| 同步 | **事件位(置位语义)+ 可选 SPSC 环形缓冲** | 事件负责"唤醒",缓冲负责"不丢数据"(D2) |
| 内存 | **全静态**:描述符只读,运行时状态固定大小 | 无堆、占用可预算 |
| 功能分层 | **调度核心必选;环形缓冲、零拷贝、监控为编译期可选模块** | 不用的功能不占代码和 RAM(D12) |

(D1–D6 为已决问题编号,见 05 篇第 4 节。)

## 2. 任务模型

### 2.1 任务描述符(只读,由生成器根据描述文件产生,见 06 篇)

| 字段 | 含义 |
|---|---|
| `name` | 调试用名称 |
| `prio` | 优先级,全表唯一;生成器按它排序并分配位图位号 |
| `trigger` | 触发方式:`PERIODIC`、`EVENT`(二者可组合),或单独的 `BACKGROUND` |
| `period` | 周期(抽象时间单位,见第 5 节) |
| `offset` | 首次释放的偏移,用于错开同周期任务 |
| `event_mask` | 关心的事件位 |
| `budget` | 单步执行时间预算,0 = 不检查 |
| `alive_window` | 存活监控窗口,0 = 不监控 |
| `again_limit` | 连续返回 `AGAIN` 的上限,达到后让出一次;0 = 不限制 |
| `on_error` | 错误策略:`IGNORE` / `RESTART` / `STOP` / `FATAL` |
| `max_restart` | 连续重启上限,超过后升级为 `FATAL` |
| `init` / `run` / `done` | 生命周期回调;`init`、`done` 可为空 |
| `ctx` | 任务私有状态的指针,内核不解释其内容 |

### 2.2 任务运行时状态(内核私有,固定大小)

| 字段 | 含义 |
|---|---|
| `state` | 生命周期状态,见 2.4 |
| `restart_cnt` | 连续重启次数 |
| `again_cnt` | 连续 `AGAIN` 次数 |
| `flags` | 内部标志(闹钟已设置等) |
| `events` | 待处理事件位 |
| `next_release` | 下一次周期释放时刻 |
| `alarm_at` | 一次性闹钟时刻 |
| `last_alive` | 最近一次成功完成一步的时刻 |
| `max_step` | 观测到的最长单步时间 |
| `overrun_cnt` / `miss_cnt` | 超预算次数 / 错过周期次数 |

按 32 位 tick 估算,每任务约 28 字节。"是否就绪"不存放在这里,而是由全局位图表示(第 3 节)。

### 2.3 `run` 的返回值

| 返回值 | 含义 |
|---|---|
| `SOS_RUN_OK` | 本步完成,等待下一次触发 |
| `SOS_RUN_AGAIN` | 工作未完成,请求尽快再次调度(不等待触发条件) |
| `SOS_RUN_STOP` | 任务正常结束,不再调度 |
| `SOS_RUN_ERR` | 出错,按 `on_error` 处理 |

### 2.4 任务生命周期

```
              sos_init()
                  │
                  ▼
           ┌─────────────┐   init 失败 → 按 on_error
           │   DORMANT   │────────────────────────────┐
           └──────┬──────┘                            │
                  │ init 成功                          │
                  ▼                                   ▼
           ┌─────────────┐   触发条件满足    ┌─────────────┐
    ┌─────►│   WAITING   │────────────────►│    READY    │◄──┐
    │      └─────────────┘  (置就绪位)       └──────┬──────┘   │
    │             ▲                               │ 被选中    │ AGAIN
    │       OK    │                               ▼          │(达到上限时
    │             │                        ┌─────────────┐   │ 先让出一次)
    │             └────────────────────────│   RUNNING   │───┘
    │                                      └──┬───────┬──┘
    │                                ERR /    │       │ STOP
    │                               存活失效   ▼       ▼
    │   RESTART: done → init       ┌─────────────┐ ┌─────────────┐
    └──────────────────────────────│    ERROR    │ │   STOPPED   │
                                   └──────┬──────┘ └─────────────┘
                                          │ FATAL      ▲ STOP 策略
                                          ▼
                                     sos_fatal()(不返回)
```

## 3. 就绪位图

### 3.1 结构

| 对象 | 含义 |
|---|---|
| `ready_bits` | 第 i 位为 1 表示优先级排名第 i 的前台任务就绪;第 0 位优先级最高 |
| `deferred_bits` | 本轮被"让出"的任务(第 4 节) |
| `next_due` | 所有等待中任务的最早释放/闹钟时刻(缓存) |

- 位号由生成器按优先级排序后分配,运行期不再比较优先级。
- 第一版使用单个 32 位字,即**前台任务 ≤ 32 个**。超过时扩展为两级位图(组位图 + 组内位图,最多 32×32),接口不变。
- 后台任务不进位图,单独以轮转方式在空闲槽运行。

### 3.2 最高优先级查找

"最高优先级就绪任务" = `ready_bits` 中最低的置位位。

- **内核自带可移植实现**:先隔离最低置位位,再用乘法散列 + 32 项查表得到位号。常数时间,只用标准 C 整数运算,不依赖任何特殊指令。
- **可选加速**:平台适配可以通过配置把该操作替换为平台自身的等价能力。这是可选的优化入口,不属于必须实现的平台契约。

### 3.3 谁会修改就绪位

| 来源 | 动作 | 上下文 |
|---|---|---|
| 事件置位 | 在互斥区内 `events |= bits`;若 `events ∧ event_mask ≠ 0` 则置该任务就绪位 | 任务或异步上下文 |
| 时间到达 | 仅当 `now` 到达 `next_due` 时扫描时间触发的任务,置就绪位并重算 `next_due` | 调度循环 |
| 派发 | 派发前清除就绪位;返回 `AGAIN` 时重新置位 | 调度循环 |

由于 `next_due` 的缓存,时间扫描只在"确实有任务到期"时发生,常规路径是常数时间。
由于"派发前清位、事件到达时置位",任务运行期间到达的事件不会丢失。

## 4. 调度算法

### 4.1 主循环(`sos_start()` = 反复调用 `sos_poll()`,空闲时等待)

以下伪代码与 v0.6 的实现一致(`kernel/src/sos_sched.c` 的 `sos_poll` / `l_dispatch`)。

```
poll:
  now ← time_now()

  ① 维护
     若 now 已到达 next_due:
        对等待中的时间触发任务:到达 next_release 或 alarm_at 的置就绪位
        (闹钟到期同时置 SOS_EV_ALARM);重算 next_due
     supervise(now)                         监控检查(每 HEALTH_MIN_INTERVAL 至多一次)
     ring_service()                         推迟的溢出钩子(D15)

  ② 选择
     candidates ← ready_bits ∧ ¬deferred_bits
     若 candidates = 0 → 转 ⑥
     T ← candidates 中最低置位位对应的任务

  ③ 派发 T 的一步
     在互斥区内:清除 T 的就绪位;ev ← T.events;T.events ← 0
     current ← T;r ← T.run(T.ctx, ev);current ← 无
     记录单步时间 max_step、本次工作的步数 job_steps / max_job_steps;检查预算
     清除"优先级不低于 T"的任务的让出标记(D13):
        T 是前台任务 → deferred_bits ← deferred_bits ∧ ¬(编号 ≤ T 的位)
        T 是后台任务 → deferred_bits ← 0
     (比 T 低的任务若在让出,标记保留:较高的任务插进来不算给出机会)

  ④ 处理返回值
     T 自己请求了 stop / restart → 执行之,跳到 ⑤
     OK    → again_cnt ← 0;周期任务推进 next_release(无错过周期时不做除法);last_alive ← now
     AGAIN → last_alive ← now;重新置 T 的就绪位;again_cnt++
             若 again_limit > 0 且 again_cnt ≥ again_limit:置 T 的让出标记;again_cnt ← 0
     STOP  → 调用 done(以 T 的身份);STOPPED
     ERR   → 错误策略(第 9 节)
  ⑤ 执行本步中登记的、针对其他任务的 stop / restart(D16);返回"已运行"

  ⑥ 空闲槽
     若存在后台任务 → 轮转派发其中一个的一步(同 ③④⑤);它清除全部让出标记
     否则若有被让出的任务 → deferred_bits ← 0,立即派发就绪任务中最高的一个
     否则 → 返回"空闲",截止时刻 = min(next_due, 下一次监控检查)
            sos_start 随后调用 on_idle 钩子与 wait_until(截止时刻)
```

### 4.2 设计要点

- **每次只派发一个**:派发后立即重新评估,高优先级任务最多只需等待正在执行的那一步。
- **后台任务只在空闲槽运行**:它们只消耗前台任务剩下的时间。
- **等待前的检查**:有被让出的任务时绝不进入等待,否则会人为延迟。
- **监控照常**:空闲等待的截止时刻包含下一次监控检查,所以健康信号在空闲时也按时发出。

### 4.3 周期释放

- 按 `next_release += period` 推进,避免累计漂移。
- 推进后仍不晚于 `now`(整个周期被错过):`miss_cnt++`,对齐到 `now` 之后的下一个周期点,不补跑。
- `offset` 用于把同周期任务的释放时刻错开。

## 5. `AGAIN` 让出机制(D3)

### 5.1 问题

一个持续返回 `AGAIN` 的任务会一直占据它的优先级,所有比它低的前台任务和后台任务都得不到运行。

### 5.2 规则

任务连续返回 `AGAIN` 达到 `again_limit` 次后,被标记为"让出":

1. 它在选择中被排除(仍保持就绪,不会丢失工作),**直到机会真正给出**;
2. 机会给出 = 一个**比它低**的前台任务运行了一步,或空闲槽运行了(后台任务的一步,或者没有任何其他工作);
3. 此时让出标记清除,它重新参与竞争,通常立即被选中。

比它**高**的任务完全不受影响——它们本来就会先被选中。**高优先级任务在其间运行,不算给出了机会**(D13):让出标记保持,高优先级任务结束后,机会仍然交给较低的任务。(v0.5 之前任何一次派发都会清除标记,使得在让出时刻恰好就绪的高优先级任务"吃掉"了低优先级任务的机会;v0.5.1 修正,并有专门的反例测试。)

### 5.3 效果

在持续负载下,只要比让出者更高的任务**不是始终就绪**,低优先级任务每 `again_limit` 步至少获得一次执行机会。若更高优先级的任务始终就绪,按严格优先级它们一直先运行,这个保证不成立(见 5.4)。`again_limit` 越小越公平,但持续任务的吞吐量越低;生成器给出的默认值为 0(不限制),由用户按任务设定。

### 5.4 让出机制管不到的情况

让出只针对**连续返回 `AGAIN`**。如果高优先级任务每一步都返回 `OK`,但事件持续到来使它不断重新就绪,它就会一直被优先选中,低优先级任务可能长期得不到运行。这是**严格固定优先级调度的本意**,内核不会改变它:

- 内核保证的是**单步有界**(任何任务最多等一步),不保证**低优先级任务的执行机会**;后者取决于高优先级任务的就绪模式,需要通过第 12 节的响应时间分析(用事件的最小到达间隔)来确认。
- 这种饥饿会被**发现**:给低优先级的周期任务(如心跳)设置 `alive_window`,饿死时存活失效,健康信号停止(8.2、8.3)。
- 若某个事件源可能"淹没"高优先级任务,应在源头限流(例如用环形缓冲收集、每步只处理 K 个、再返回 `AGAIN` 进入让出机制),而不是依赖调度器。

## 6. 事件与环形缓冲(D2)

### 6.1 事件

- 事件位是"置位"语义,多次置位等同一次,只表达"有事发生",用于唤醒任务。
- 只有含 `EVENT` 触发的任务会被事件唤醒;其他任务收到的事件位会保留,随它下一次运行一起交付。
- 优先级唯一,不存在平局。

### 6.2 SPSC 环形缓冲

当数据可能连续到达、不能丢失时,使用内核提供的环形缓冲 `sos_ring`:

| 性质 | 规定 |
|---|---|
| 生产者/消费者 | **恰好一个生产者执行流、一个消费者任务**。"一个生产者"指一个执行流,而不是一个函数:两个不同优先级的中断即使调用同一个写入函数,也已违反前提 |
| 归属(D11) | 描述符记录生产者任务(异步上下文记为无)和消费者任务;归属任务被停止或重启时,内核放弃它未完成的原地操作(见 6.2.1 第 4 条) |
| 存储 | 静态分配;元素大小固定;容量为 2 的幂 |
| 满时 | 拒绝写入,返回"满",溢出计数加一(丢弃最新数据,保留已有数据) |
| 与事件绑定 | 可选地绑定一个消费者任务和事件位:写入成功时自动给消费者置事件 |
| 并发保护 | 只在发布读/写索引时进入互斥区;元素拷贝在互斥区外完成(单生产者单消费者下槽位所有权互斥) |
| 声明方式 | 在描述文件中声明,由生成器产生存储与句柄(06 篇) |

### 6.2.1 两种访问方式(D8)

| 方式 | 生产者 | 消费者 | 适用 |
|---|---|---|---|
| **按值拷贝** | `put`:把元素拷入缓冲 | `get`:把元素拷出缓冲 | 小元素;最简单 |
| **原地访问(零拷贝)** | `reserve` 取得空槽指针 → 原地写入 → `commit` 发布 | `acquire` 取得队首元素指针 → 原地读取 → `release` 归还 | 大元素;避免两次拷贝 |

原地访问的规则:

1. **槽位所有权**:`reserve` 到 `commit` 之间,该槽只属于生产者;`acquire` 到 `release` 之间,该槽只属于消费者。指针只在这段区间内有效。
2. **每端最多一个未完成操作**:生产者在 `commit` 前再次 `reserve` 返回同一个槽(幂等),消费者在 `release` 前再次 `acquire` 返回同一个元素。未完成期间不得在同一端混用 `put` / `get`。
3. **满/空**:`reserve` 在缓冲满时返回空指针并计入溢出;`acquire` 在缓冲空时返回空指针。
4. **放弃**:生产者可以不 `commit`(下次 `reserve` 得到同一个槽,内容视为未写);消费者必须 `release`,否则该元素一直占位。**归属任务被停止或重启时(D11)**,内核自动放弃它的未完成操作:生产者预留的槽位被丢弃(从未发布,消费者看不到);消费者取用中的元素**保留在队列中**,重启后再次交付——数据不丢,但若正是这个元素导致任务出错,重启会再次失败,最终由 `max_restart` 升级为 `FATAL`。
5. **事件通知**:只在 `commit` 时触发,与 `put` 相同。
6. **跨步持有**:消费者可以在一步中 `acquire`、返回 `AGAIN`、下一步再 `release`,用于分步处理大元素;此时该元素占位的时间计入缓冲容量规划。
7. **异步上下文**:`reserve` / `commit` 可在异步上下文中调用;两者之间的写入必须短而有界。

**为什么用互斥区而不做无锁实现**:无锁需要平台提供内存序保证,会扩大平台契约。用已有的互斥区能力,在所有平台上都正确。将来若需要,可增加一个可选的"内存屏障"能力来实现无锁版本,接口不变。

### 6.3 推荐的消费模式

事件只说明"缓冲非空"。消费者在一步中最多取出 K 个元素(K 由任务自定,用于限制单步时间);若取完 K 个后仍非空,返回 `AGAIN`。这样既不丢数据,又保持单步有界,并受第 5 节让出机制的约束。

## 7. 抽象时间

### 7.1 两层时间单位

| 层 | 单位 | 使用者 | 说明 |
|---|---|---|---|
| 配置时间 | `SOS_TIME_UNIT`(默认 1 µs) | 描述文件、任务 API | 与平台无关 |
| 内部时间 | tick | 内核内部 | 来自平台时间源;`sos_init` 时一次性换算 |

换算只依赖平台提供的速率常量 `SOS_PLATFORM_TICKS_PER_SEC`。

### 7.2 时间源的抽象要求

1. **单调**:除自然回绕外不倒退。
2. **自然回绕**:宽度 W 位(`SOS_PLATFORM_TICK_BITS`,16 / 32 / 64)。
3. **随时可读**:不阻塞、无副作用、任何上下文可调用。

### 7.3 比较规则与范围检查

- 时刻比较一律用"差值转有符号后与 0 比较",回绕安全。
- 可正确比较的最大间隔为 2ᵂ⁻¹ / 速率。
- 所有 `period`、`alive_window` 及运行期闹钟上限必须小于该间隔的一半。生成器在已知目标平台参数时于构建期检查;`sos_init` 在运行期再检查一次作为兜底。

### 7.4 精度要求

时间源分辨率应不大于最小 `budget` 的 1/10。不满足时记录警告,但仍可启动。

## 8. 监控

### 8.1 执行时间预算

每步计时;超过 `budget` 时 `overrun_cnt++` 并调用钩子表中的 `on_overrun`。默认只记录;配置 `SOS_CFG_OVERRUN_IS_ERROR = 1` 时按任务的 `on_error` 处理。

协作式内核无法打断正在运行的一步,所以三件事要分清:

| 问题 | 由谁保证 |
|---|---|
| 一步**结束后**发现它超了预算 | 内核(本节):事后检测、计数、钩子、可选按错误处理 |
| 各任务的**最坏响应时间** | 设计期分析(第 12 节),以各任务的 `budget` 作为 WCET 输入;budget 本身不强制任何东西 |
| 一步**永不返回**(死循环、阻塞) | 内核之外:平台的健康信号超时(硬件看门狗等)复位系统(8.3) |

### 8.2 存活监控

设置了 `alive_window` 的任务,若 `now − last_alive > alive_window`,判为失效并按 `on_error` 处理。

实现细节(v0.2):

- 检查与健康信号共用一个节拍,每 `SOS_CFG_HEALTH_MIN_INTERVAL` 最多执行一次;内核空闲时的等待截止时刻也会算入下一次检查,所以空闲期间监控照常进行。
- 一次失效只记录、只处理一次;任务下一次完成一步(`OK` 或 `AGAIN`)才算恢复。`IGNORE` 策略下,失效期间健康信号持续停止。
- 对事件任务,存活窗口的含义是"至少每隔这么久应当收到一次事件";没有事件来源保证的事件任务不应设置存活窗口。
- 失效不会推进周期任务的释放时刻(它可能只是被饿死,而不是出错)。

### 8.3 健康信号

每次派发后和空闲槽中评估,满足以下全部条件时调用平台健康信号能力:

1. 没有任务处于存活失效状态;
2. 没有进入 `FATAL`;
3. 距上次发出已超过 `SOS_CFG_HEALTH_MIN_INTERVAL`。

健康信号不以"系统空闲过"为条件;过载检测交给存活监控(给一个低优先级周期任务设置 `alive_window`)。

**设计约束**:最长单步时间 + 内核开销 < 平台的健康信号超时时间。

## 9. 错误处理

| 策略 | 行为 |
|---|---|
| `IGNORE` | 只记录,任务回到 WAITING |
| `RESTART` | `done` → `init`,`restart_cnt++`;超过 `max_restart` 升级为 `FATAL`;任务成功完成一步后计数清零 |
| `STOP` | `done`,任务进入 STOPPED,其他任务继续 |
| `FATAL` | `sos_fatal(原因)` → 钩子表 `on_fatal` → 平台安全停机,不返回 |

所有错误写入固定深度的环形错误日志(任务号、错误码、时刻)。

## 9.1 生命周期回调的身份与跨任务控制(D16)

- `init` 与 `done` 执行时,"当前任务"就是它们所属的任务:其中调用 `sos_task_self()`、设置闹钟、按归属检查环形缓冲,都作用于该任务(而不是触发这次调用的任务)。
- 在一个任务的 `run`(或 `init` / `done`)中对**另一个**任务调用 `sos_task_stop` / `sos_task_restart`,只登记请求;请求在当前这一步返回后、下一次选择之前执行。因此一个任务的一步里永远不会包含另一个任务的 `init` / `done`,执行时间也只归属于各自的任务。对自己的请求同样在本步返回后生效。
- 在主上下文(不在任何回调中)调用时立即执行。
- 后一次请求覆盖前一次(先 stop 后 restart = restart)。

## 10. 启动流程

```
平台准备(内核之外)
   前置条件:C 运行环境就绪;时间源可读;互斥区可用
      │
      ▼
sos_init(&sos_cfg_root)                ← 由生成器产生的配置根对象
   ├─ 校验配置根:ABI 版本号、生成器版本号、配置摘要(06 篇)
   ├─ 运行期兜底校验(始终执行,仅启动时一次):
   │    优先级有序且唯一、触发组合合法、时间范围(7.3)、精度(7.4)
   ├─ 换算配置时间为 tick;清零运行时状态;首次释放 = now + offset;计算 next_due
   ├─ 初始化所有环形缓冲
   └─ 按优先级顺序调用各任务 init;失败时按其 on_error 处理
      │
      ▼
sos_start()   不返回
```

## 11. 共享数据

- **任务 ↔ 任务**:没有抢占,在 `run` 中访问共享数据无需加锁。
- **异步上下文 ↔ 任务**:异步上下文只允许调用 `sos_event_set_async` 和 `sos_ring_put`;其他共享数据由任务在 `sos_critical_enter / exit` 内访问。

## 12. 可调度性分析(非抢占固定优先级)

分析对象是**一次工作(job)**:任务的一次释放,可能由多步(`AGAIN`)完成。记号:

| 记号 | 含义 | 描述文件字段 |
|---|---|---|
| Cᵢ | 单步最坏执行时间 | `budget` |
| nᵢ | 一次工作最多的步数 | `max_steps`(缺省按 1 计,报告中注明该假设) |
| 释放流 | 周期流(`period`)与事件流(`min_interarrival`)**相互独立、次数相加**(D17):窗口 R 内释放至多 Σ⌈R/T⌉ 次。只取较小间隔会算少——事件恰在周期释放之前和之后各来一次。事件触发的任务没有 `min_interarrival` 时,速率未知 | `period`、`min_interarrival` |
| Dᵢ | 一次工作的期限 | `deadline`(缺省 = Tᵢ) |
| Lᵢ | 让出阈值 | `again_limit` |

```
Rᵢ = kᵢ · Bᵢ + nᵢ · Cᵢ + Σ_{j ∈ hp(i)} relⱼ(Rᵢ) · nⱼ · Cⱼ        relⱼ(R) = Σ_{j 的每条释放流} ⌈R / T⌉

Bᵢ = max_{k ∈ lp(i) ∪ bg} Cₖ          一步阻塞:更低优先级或后台任务的一步刚开始
kᵢ = 1 + ⌊(nᵢ − 1) / Lᵢ⌋(Lᵢ = 0 时为 1)  每次让出再放进一个较低的步
```

迭代求解。生成器 `sosgen` 按此公式输出估算,结论分四类:

| 结论 | 含义 |
|---|---|
| PASS | 所需输入全部给出(含 `max_steps`),且 Rᵢ ≤ Dᵢ |
| CONDITIONAL | Rᵢ ≤ Dᵢ,但本任务或更高优先级任务的 `max_steps` 未给出、按 1 计——结论只在该假设成立时有效 |
| FAIL | Rᵢ > Dᵢ |
| N/A | 缺少必要输入(预算、速率),不作结论 |

Cᵢ 可加上每步的内核开销(`[kernel] dispatch_overhead`,应取目标板实测值)。报告列出**未计入**的部分:释放扫描与监控检查、平台等待/唤醒延迟、中断处理、以及任务步之外的一切。

`max_steps` 是**需要验证的设计假设**,内核不强制它;内核统计每个任务实际最长的工作步数(`sos_task_get_stats` 的 `max_job_steps`),在目标板上与之核对。

演进:v0.5 之前按"每次释放一步"并优先取周期;v0.5.1 改为取较小间隔、按工作建模;v0.5.2 改为两条释放流相加并区分 PASS / CONDITIONAL。

该分析是设计期估算:Cᵢ 是假设值,必须在目标平台上实测核对(v0.6 验收清单第 6 项)。

编码规范:**每一步必须短而有界**,耗时操作拆成多步并返回 `AGAIN`。经验值:单步时间 ≤ 系统最短周期的 1/10。

## 13. 抽象示例:两级流水线

| 任务 | 优先级 | 触发 | 说明 |
|---|---|---|---|
| `ingress` | 0 | `PERIODIC` + `EVENT(INPUT)` | 异步上下文把原始输入写入环形缓冲 `rx_ring`(绑定 `INPUT` 事件);任务每步最多取 K 个组装请求;完整请求写入 `req_ring`(绑定 `worker` 的 `REQ_READY`) |
| `worker` | 1 | `EVENT(REQ_READY)` | 从 `req_ring` 取请求处理;耗时处理分步 `AGAIN`,`again_limit = 8`;响应就绪后给 `ingress` 置 `RESP_READY` |
| `heartbeat` | 2 | `PERIODIC` | 设置 `alive_window`,作为过载探测器 |
| `selfcheck` | — | `BACKGROUND` | 空闲时分块自检 |

```
时间 →
ingress    ■     ■■■    ■            ■
worker            ■■■■■■■■ ■■■■        (连续 8 次 AGAIN 后让出一次)
heartbeat  ■               ▲ 借到让出的机会
selfcheck   ▪▪▪▪                ▪▪▪   (只填充空闲时间)
```

两级之间只通过环形缓冲和事件通信,互不调用。
