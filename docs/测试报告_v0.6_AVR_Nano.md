## T1 等待与通知的竞态

**做法**(`t1_race/main.c`):单个事件任务 E,无周期任务,`SOS_CFG_SUPERVISE_ENABLE 0`,空闲时下一次自然唤醒约 245.76 ms(OCR1A 最远 0xF000 tick)。E 每步结束时重新启动 Timer2 单次中断,OCR2A 在 1…255 循环,预分频 /1、/8、/64 轮换(派发单要求 /8、/64,另加 /1 以 1 周期步长覆盖 E 返回后的前 255 个周期),中断落在 E 返回后 1–16 384 个周期之间,扫过"返回 → poll → 判定空闲 → 进入睡眠"的每个位置。ISR 记 `sos_time_now()` 再 `sos_event_set_async`;握手保证一次中断对应一步,无合并。

| 项 | 模拟器 | 实物板 |
|---|---|---|
| 事件总数 / ISR 次数 / 不匹配 | 100 000 / 100 000 / 0 | |
| 延迟 最小 / 最大 | 60 µs / **104 µs**(最大出现在 /1、OCR = 7) | |
| 直方图 <50 µs / <200 µs / <1 ms / ≥1 ms / ≥200 ms | 0 / 100 000 / 0 / 0 / **0** | |
| 每个预分频 | /1:33 405,/8:33 405,/64:33 190,全部落在 50–200 µs | |
| `sos_error_count()` | 0 | |

**对照通过标准**:全部处理 ✓;最大 < 1 ms ✓;无 ≥ 200 ms ✓ → **PASS**。
延迟下限约 60 µs:这是 ISR 剩余部分 + 唤醒 + 一次 `sos_poll` + 派发的固定开销(与 T4.4 一致)。

**附加:测试自身的有效性**(`t1_race/avr_platform_mutant.c`,只删掉 `wait_until` 开头的粘滞检查,不回提交):

| 项 | 变异体 |
|---|---|
| 最大延迟 | **245 848 µs**(= 0xF000 tick,正是下一次自然唤醒) |
| ≥ 200 ms | **2096 次**;1 ms–200 ms 另有 1965 次 |
| 分布 | /1:0 次;/8:1703 次 ≥ 200 ms;/64:393 次 |
| 判定 | FAIL —— 测试能抓到丢失唤醒 |

/1 一次也没触发,说明竞态窗口位于 E 返回后 255 个周期之外(poll 计算下一个截止时刻之后、`wait_until` 关中断之前);/8 的 8 周期步长正好扫过它。

## T2 高频事件与环形缓冲

**做法**(`t2_ring/main.c`):环形缓冲 `rx`(`uint16_t` × 32,生产者 = 异步上下文,消费者 C,`notify` → C)。Timer2 CTC 以 1 / 5 / 10 kHz 写入 16 位递增序号,FULL 只计数不重试。C 每步最多取 8 个并检查连续性,仍有数据返回 `AGAIN`。B(低优先级,10 ms)每步忙等 0.5 ms。每档 600 s。

> 与派发单的偏差:除 C、B 外另加了两个任务——最高优先级的定序任务 S(100 ms,只负责计时和启停生产者,每步几微秒)和最低优先级的打印任务 R。最初让 B 兼做定序,结果 10 kHz 档 B 被完全饿死、测试走不完,所以拆开;打印放到生产者停止之后、最低优先级任务里,不污染测量。

| 档 | 写入 | 收到 | FULL | 缺口 | 重复 | `overflow_cnt` | `high_water` | C 最长步 / 最多连续步 | B 错过周期 | 空闲唤醒 | 结果 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 kHz | 605 080 | 605 080 | 0 | 0 | 0 | 0 | 1 | 44 µs / 1 | 0 | 664 690 | PASS |
| 5 kHz | 3 000 000 | 3 000 000 | 0 | 0 | 0 | 0 | 5 | 216 µs / 1 | 0 | 1 252 666 | PASS |
| 10 kHz | 6 000 003 | 6 000 003 | 0 | 0 | 0 | 0 | 8 | 468 µs / 3 | **60 000(全部)** | **21** | PASS(数据) |
| 实物板 | | | | | | | | | | | |

**对照通过标准**:三档 `收到 + FULL = 写入`、无重复、无未计数缺口、`overflow_cnt` 与 FULL 一致 → **PASS**。

**观察(重要)**:10 kHz 时 600 s 内只空闲了 21 次,B 的 60 000 个周期一个都没跑上——每个元素的"中断 put + notify + 唤醒 + poll + 派发 + get"约 2300–2500 周期(由 T4 各项相加估算),单元素中断在 Nano 上可持续的上限约 6–7 kHz。到 10 kHz 内核仍保证数据不丢,但它是靠 C 一直占着 CPU、低优先级任务饿死换来的。建议在 `platform/avr_nano/README.md` 写明这个量级,并提示高频源应批量入队。

1 kHz 档写入数为 605 080(约 605 s)而不是 600 000:这是 simavr 的 TIFR1 写入偏差造成的内核时间丢失(「测量环境的局限」S1),不影响数据结论。

日志:`logs/t2_ring.sim.log`。

## 推荐参数

- **`dispatch_overhead = 96 µs`**(按派发单规则)
  依据:T4.1 在 8 个任务时最大 1474 周期 = 92.12 µs,向上取整到 4 µs 的倍数得 96 µs(1536 周期)。AVR 没有缓存和流水线差异,派发路径本身是确定的(10 000 次中 9 999 次都是 1427 周期),只有中断会拉长;96 µs 比确定路径高 7.6 %,比实测最大值高 4.2 %,足以覆盖一次 Timer1 溢出中断落进来的情况。
- **需要 smartOs 侧决定的一点**:T4.1 的定义(空 `run` 返回 `AGAIN`)没有走 `l_advance_release`。周期任务每完成一步实际是 **148 µs**(T4.2 普通派发 p99.9 = 2368 周期),比 96 µs 高约 50 %。如果描述文件里有周期任务,按 96 µs 算的 schedulability 是偏乐观的。两个选择:(a)`dispatch_overhead` 取 **152 µs**(148 向上留一档余量);(b)先去掉每步的除法(见问题 F1),再重测 T4.1/T4.2,两者应接近 90 µs。

**用推荐值重跑 sosgen**(`examples/layered_pipeline/app.toml`,`--tick-bits 32 --ticks-per-sec 250000`,输入与完整报告在 `t4_overhead/sosgen/`):

| 任务 | overhead 0 | 96 µs | 152 µs |
|---|---|---|---|
| ingress | PASS: R = 300 ≤ D = 400 | **FAIL**: R = 492 > 400 | FAIL: R = 604 > 400 |
| worker | PASS: R = 1320 ≤ 3600 | **FAIL**: R = 3944 > 3600 | FAIL: R = 13 576 > 3600 |
| heartbeat | PASS: R = 1180 ≤ 5000 | **FAIL**: R = 535 564 > 5000 | FAIL: R = 541 368 > 5000 |

**结论变了**:这个示例的预算(ingress 100 µs、worker 200 µs、heartbeat 20 µs)是按快得多的目标写的,在 Nano 上每步开销本身就接近或超过预算。加上 96 µs 后,ingress 一个就占 69 %(1 ms 周期 + 400 µs 到达间隔,每次 196 µs),worker 占 74 %(1.2 ms 一次请求 × 3 步 × 296 µs),合计已超过 100 %,heartbeat 的响应时间发散。sosgen 把这种情况报告为"R = 535 564",那是迭代到 `R > 100·D` 时截断的值,不是真实响应时间(问题 F5)。

## T5 故障恢复

每项一个固件(`t5_fault/main.c`,`T5_CASE`)。故障只在上电/刚烧录后的第一次启动注入;由看门狗引起的启动(MCUSR 含 WDRF)不注入,干净运行 3 s 后打印 `clean run OK`——这样一次上电就是一个完整的"故障 → 复位 → 恢复"序列。启动计数放在 EEPROM。时间取自模拟时间戳(实物板用 `tools/serial_log.py` 的主机时间戳)。

## T6 长时间压力运行

**做法**(`t6_soak/main.c`):T2 的生产者 5 kHz(Timer2 → 环形缓冲 → C)+ T1 式相位扫描单次中断(Timer0 → E)+ 两个周期任务(F 50 ms,S 1 s)+ 看门狗。每 600 s 打印 5 行统计,每次 tick 回绕打印一行 `WRAP`。

> **与派发单的偏差,及原因**:第一版照搬 T1 的"处理完立即再触发",E 每秒触发约 2200 次,叠加 5 kHz 后**超出 Nano 的 CPU**——20 s 内环形缓冲 FULL 占 23 %(22 824 / 100 003)、F 错过 139 个周期、T1 最大延迟 2.8 ms。另外,S 若在一个步里用平台的轮询串口打印整段报告要 2.6 ms,非抢占下会直接推高 E 的延迟。现行版本:E 处理完设 10 ms 闹钟,闹钟到再启动下一次 Timer0 单次中断(相位扫描不变,约 93 次/秒);打印由最低优先级任务每步拼一行,经测试项目自己的 UDRE 中断发送缓冲输出,任何一步都远小于 1 ms。超载那组数据作为 F3 的旁证保留。

模拟器无法在合理时间内跑 24 h(这组负载下约 2.2 倍实时)。分两路:

1. **时间跳跃**(`logs/t6_soak_warp.sim.log`):固件打印开机横幅后(`avr_platform_init` 之后、`sos_init` 之前),由测量台把平台的软件溢出计数 `l_ovf` 预置为 0xECA1,使回绕发生在约 1300 s;固件与 smartOs 均未改动。运行 3700 s 模拟时间。
2. **自然运行**(`logs/t6_soak.sim.log`):从 tick = 0 开始,截至报告时已运行 5400 s 模拟时间,继续在跑。

## 实物板执行步骤

1. 克隆 smartOs 到 `239ced2`,与本目录并列(或 `make SOS_ROOT=...`)。`make` 生成 `build/*.hex`。
2. 每个用例:`make flash-<名字> PORT=/dev/cu.wchusbserial*`(老 bootloader 57600,Optiboot 加 `UPLOAD_BAUD=115200`),然后 `python3 tools/serial_log.py <端口> logs/<名字>.board.log`。
3. **T1**:`t1_race`(约 40 s),可选 `t1_mutant`(约 10 分钟)。看最后 `T1 PASS`。
4. **T2**:`t2_ring`,约 30 分钟。
5. **T4**:按 README 接逻辑分析仪(D8、D9、D11、GND);依次烧 `t4_1_n1/n4/n8`、`t4_2_n1/n4/n8`、`t4_3`、`t4_4_idle`、`t4_4_busy`、`t4_5`、`t4_6_n4/n8`、`t4_6_base_n4/n8`、`t4_7`,每个采到 `@@END` 为止;CSV 导出后 `tools/la_to_edges.py` → `logs/<名字>.edges`,再 `tools/t4_analyze.py logs` 得到同格式的表,与「T4」对照。
6. **T5**:每个 `t5_N` 烧录后**断电再上电**一次(保证首个启动带 PORF、注入故障),记录到 `clean run OK`。重点看 T5.1/T5.4 `HALT` 行到下一个 `== T5` 横幅的间隔(期望约 15 ms + 启动时间)。T5.6:先让它自己跑完 20 次看门狗循环(约 1 分钟,`--keep`),再手动断电/上电 20 次,每次横幅应带 `PORF`、`power_on` 递增。
7. **T6**:`t6_soak`,`serial_log.py --keep`,≥ 24 h。每 10 分钟 5 行;回绕时一行 `WRAP`(约每 4.77 h 一次)。
