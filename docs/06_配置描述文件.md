# 06 配置描述文件与生成器(D4)

## 1. 为什么用描述文件

| 手写 C 数组的问题 | 描述文件 + 生成器的做法 |
|---|---|
| 必须手工按优先级排序 | 用户只写优先级,生成器排序并分配位图位号 |
| 优先级重复、事件位冲突要到运行时才发现 | 构建期报错,带文件名和表项位置(如 `app.toml: task[1] 'worker': ...`;标准库 TOML 解析器不提供行号) |
| 任务 id、事件位、缓冲句柄要手工维护常量 | 自动生成具名常量 |
| 配置与内核版本不匹配无从察觉 | 生成版本号与配置摘要,`sos_init` 校验 |

## 2. 格式选择:TOML

- 人可读、支持注释、层级简单,足以表达任务表。
- 生成器用 Python 3.11+ 编写,TOML 解析在标准库中(`tomllib`),**无第三方依赖**。
- 描述文件本身与平台无关;平台参数(计数宽度、速率)作为可选的"平台概要"单独提供。

## 3. 描述文件结构(示意)

完整可运行的版本见 [examples/layered_pipeline/app.toml](../examples/layered_pipeline/app.toml)。以下只用于说明结构:

```toml
[kernel]
time_unit_us        = 1
errlog_depth        = 8
overrun_is_error    = false
health_min_interval = "10ms"

[hooks]                         # 每项可省略;值为 C 函数名
on_fatal    = "app_on_fatal"
on_overrun  = "app_on_overrun"

[[task]]
name         = "ingress"
prio         = 0
trigger      = ["periodic", "event"]
period       = "1ms"
events       = ["INPUT", "RESP_READY"]   # 生成 SOS_EV_INGRESS_INPUT 等
budget       = "50us"
on_error     = "restart"
max_restart  = 3
init = "ingress_init"
run  = "ingress_run"
ctx  = "g_ingress_ctx"

[[task]]
name         = "worker"
prio         = 1
trigger      = ["event"]
events       = ["REQ_READY"]
budget       = "100us"
again_limit  = 8
on_error     = "restart"
run  = "worker_run"
ctx  = "g_worker_ctx"

[[task]]
name         = "heartbeat"
prio         = 2
trigger      = ["periodic"]
period       = "100ms"
alive_window = "300ms"
on_error     = "fatal"
run  = "heartbeat_run"

[[task]]
name    = "selfcheck"
trigger = ["background"]
run     = "selfcheck_run"

[[ring]]
name      = "rx_ring"
elem_type = "app_frame_t"       # 由应用头文件定义
capacity  = 16                  # 必须是 2 的幂
producer  = "async"             # 异步上下文
consumer  = "ingress"
notify    = "INPUT"             # 写入成功时给 ingress 置该事件

[[ring]]
name      = "req_ring"
elem_type = "app_request_t"
capacity  = 4
producer  = "ingress"
consumer  = "worker"
notify    = "REQ_READY"

[app]
headers = ["app_types.h", "app_tasks.h"]   # 生成的 .c 需要包含的应用头文件
```

时间量一律写成带单位的字符串(`ns` / `us` / `ms` / `s`),由生成器换算成 `SOS_TIME_UNIT` 的整数倍,不能整除时报错。

字段补充说明(v0.3 实现):

| 字段 | 说明 |
|---|---|
| `on_error` | 默认 `"fatal"`(最保守) |
| `[kernel] ring_enable` | 默认:声明了 `[[ring]]` 就为 true,否则 false(不用就不编译) |
| `[kernel] ring_zero_copy` | 默认等于 `ring_enable`;只用按值接口时可关闭以减小体积 |
| `[kernel] supervise_enable` | 默认 true;关闭后内核不发健康信号 |
| `events` | 事件只唤醒含 `event` 触发的任务;其他前台任务也可以声明事件,事件位随它下一次运行一起交付 |
| `min_interarrival` | 事件的最小到达间隔,只用于可调度性估算;事件触发的任务缺少它时结论为 N/A。同时有周期与事件触发时,两条释放流**次数相加**(D17,03 篇第 12 节),不是取较小间隔 |
| `max_steps` | 可选,一次工作最多的步数(≥ 1),只用于可调度性估算;缺省按 1 计,相关结论标为 CONDITIONAL。运行时可用 `max_job_steps` 统计核对 |
| `[kernel] dispatch_overhead` | 可选,每步的内核开销,加到每个任务每一步的执行时间上;应取目标板实测值,缺省 0 |
| `deadline` | 可选,一次工作的期限,缺省等于释放间隔 |
| `ctx` | 变量名,生成器取其地址(`&g_x`);变量需在 `[app] headers` 中声明 |
| 后台任务 | 不允许 `prio`、`period`、`offset`、`events`、`alive_window`、`again_limit` |
| 未知键 | 一律报错,防止拼写错误被静默忽略 |

## 4. 生成器 `sosgen`

### 4.1 输入与输出

```
            ┌───────────────┐
 app.toml ─►│               │─► sos_cfg_gen.h   具名常量、配置摘要
            │    sosgen     │─► sos_cfg_gen.c   任务表、缓冲存储、钩子表、配置根
 平台概要 ─►│  (可选输入)    │─► sos_cfg.h       内核编译期参数
            │               │─► 报告(文本)     位号分配、内存占用、可调度性估算
            └───────────────┘
```

### 4.2 构建期检查

| # | 检查项 | 需要平台概要? |
|---|---|---|
| 1 | 前台任务优先级唯一;数量 ≤ 位图容量 | 否 |
| 2 | 触发方式组合合法(`background` 不与其他组合) | 否 |
| 3 | `periodic` 有 `period`;`event` 有至少一个事件;每任务事件 ≤ 31 个 | 否 |
| 4 | 缓冲容量为 2 的幂;生产者、消费者存在;`notify` 是消费者声明过的事件;生成的描述符记录生产者任务与消费者任务(D11) | 否 |
| 5 | 每个缓冲恰好一个生产者和一个消费者;同一任务不能既是某缓冲的生产者又是消费者 | 否 |
| 6 | 所有时间量换算后为整数 | 否 |
| 7 | 时间量在可比较范围的一半以内(03 篇 7.3) | 是 |
| 8 | 时间源分辨率满足预算精度要求(03 篇 7.4) | 是 |
| 9 | 可调度性估算:若给出各任务 `budget` 与周期,按 03 篇第 12 节公式输出响应时间上界 | 否(只用配置时间) |
| 10 | 模块开关一致(D12):声明了缓冲就不能关闭 `ring_enable`;`ring_zero_copy` 需要 `ring_enable`;关闭 `supervise_enable` 时不能有 `alive_window`,也不能打开 `health_enable` / `overrun_is_error` | 否 |

函数名和变量名是否存在,由 C 编译器和链接器检查,生成器不重复。

### 4.3 版本与摘要

生成的配置根中包含三项。哪一项由谁检查、能防住什么,如下(D14):

| 项 | 检查 | 能防住 | 防不住 |
|---|---|---|---|
| 配置 ABI 版本 | `sos_init` 与内核的 `SOS_ABI_VERSION` 比较,不等即拒绝 | 新内核配旧生成结果(结构布局不同) | — |
| 配置摘要 | `SOS_CFG_INIT()` = `sos_init_checked(&sos_cfg_root, SOS_CFG_DIGEST)`:头文件中的摘要宏,与 `.c` 表格里**写死的**摘要比对 | 头文件与表格来自不同次生成(只重新生成了一部分、或混入了旧文件) | 生成之后手工改动 `.c` 表格内容;描述文件改了却没重新生成 |
| 生成器版本 | 不检查,只用于诊断 | — | — |

版本兼容性只由 ABI 版本负责;摘要只承诺上表中"能防住"的那一种错误。手工改动生成文件不在保护范围内(生成文件头部写明"Do not edit"),但 `sos_init` 的结构性检查仍会拒绝破坏内存安全或调度正确性的配置。

### 4.4 确定性

相同的输入必须生成逐字节相同的输出(固定排序、无时间戳),便于版本管理和比对。

### 4.5 命令行

```bash
python3 tools/sosgen app.toml -o build/gen [--tick-bits 32 --ticks-per-sec 1000000] [--report report.txt]
```

高优先级负载 U ≥ 1 时,响应时间没有有限上界,报告为 `FAIL: diverges (higher-priority load U = …)`,不再输出截断的迭代值。给出平台参数时执行第 7、8 项检查;报告包含任务 id/位号分配、环形缓冲表和可调度性估算(只对设置了 `budget` 且有周期或 `min_interarrival` 的任务给出结果,其余显示 n/a)。

### 4.6 分发与调用(D9)

- 生成器以源码形式位于 `tools/sosgen/`,不单独打包;使用方在构建脚本中直接调用仓库内的源码。
- 生成器版本与仓库版本标签一致,写入配置根(4.3)。
- 生成的每个文件头部都声明该文件属于使用方、不受 MPL-2.0 约束(05 篇 3.2 节)。

## 5. 不使用生成器时

生成器是推荐路径,不是强制依赖。用户可以按 04 篇的结构手写配置根;此时构建期检查全部失效,只剩 `sos_init` 始终执行的运行期兜底检查(优先级有序且唯一、触发组合合法、时间范围与精度);缓冲的单生产者/单消费者约束无法在运行期检查。仓库中提供一份手写配置示例用于说明。
