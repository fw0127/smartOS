# 05 平台能力契约、决策记录与路线图

## 1. 平台能力契约

内核对外界的**全部**依赖就是下面的 2 个常量和 7 个函数,声明在 `platform/sos_platform.h` 中。
契约只规定**语义与性质**,不规定实现方式。

### 1.1 常量

| 常量 | 语义 | 约束 |
|---|---|---|
| `SOS_PLATFORM_TICK_BITS` | 时间源计数宽度 | 16、32 或 64 |
| `SOS_PLATFORM_TICKS_PER_SEC` | 时间源速率 | > 0;运行期不变 |

### 1.2 函数

| 能力 | 函数 | 语义 | 必须满足的性质 |
|---|---|---|---|
| 时间源 | `sos_platform_now()` | 返回当前 tick | 单调、自然回绕、不阻塞、任何上下文可调用 |
| 互斥区 | `sos_platform_critical_enter()` | 进入互斥区 | 到 `exit` 之前不会被异步上下文打断;**可嵌套**;**也必须能在异步上下文中调用且不阻塞**(内核在 `sos_event_set_async`、`sos_ring_put/reserve/commit` 中使用它);**起完整内存屏障作用**:`exit` 之前的写入,对下一个进入者可见 |
| | `sos_platform_critical_exit()` | 离开互斥区 | 与 `enter` 成对;最外层恢复进入前状态 |
| 等待 | `sos_platform_wait_until(deadline)` | 等待到 `deadline` 或被通知 | **允许提前返回**;允许直接返回(忙等平台) |
| | `sos_platform_notify()` | 让进行中的等待尽快返回 | 可在异步上下文调用;**粘滞**:若在等待开始前到达,下一次等待必须立即返回(否则"判定空闲"与"开始等待"之间到达的事件会被延迟到截止时刻);忙等平台可为空 |
| 健康信号 | `sos_platform_health_signal()` | 声明"调度正常" | 不阻塞;可为空 |
| 安全停机 | `sos_platform_halt(reason)` | 终止运行 | **不返回**;含义由平台决定 |

### 1.3 可选的平台加速(不属于契约)

| 入口 | 作用 | 未提供时 |
|---|---|---|
| `SOS_CFG_FIND_FIRST_SET` | 替换就绪位图的最低置位查找 | 使用内核自带的可移植常数时间实现 |

可选入口不影响正确性,只影响性能;契约一致性测试会验证替换后的结果与可移植实现一致。

### 1.4 前置条件

调用 `sos_init` 之前,平台必须已经:建立可运行 C 代码的环境;使时间源可读、互斥区可用;完成自身需要的任何准备(内核不感知)。

### 1.5 契约的设计取舍

| 取舍 | 理由 |
|---|---|
| 不要求周期性节拍中断 | 能读单调计数就能完成全部调度判断 |
| `wait_until` 允许提前返回、允许忙等 | 最简单的平台直接返回即可 |
| 健康信号与安全停机允许简单实现 | 无监控/复位能力的平台也能运行 |
| 环形缓冲用互斥区而非内存屏障 | 不为一个功能扩大契约(03 篇 6.2) |
| 不包含"启动"函数 | 启动高度依赖平台,内核只声明前置条件 |
| 互斥区兼作内存屏障 | 环形缓冲只在互斥区内发布读写索引,元素拷贝在外面;正确性依赖"退出前的写入对下一个进入者可见"。单核关中断天然满足;RTOS 用中断安全的临界区;多线程用互斥锁 |

**常见误用**(v0.5 起写入契约):在 RTOS 上用任务级互斥锁实现互斥区——中断里调用 `sos_event_set_async` 会阻塞或死锁。必须使用可在中断中调用的临界区原语(例如"从中断进入临界区"类接口)。

## 2. 测试策略

| 层级 | 内容 | 示例用例 |
|---|---|---|
| 单元测试 | 时间比较、事件、位图查找、环形缓冲 | 时间源最大值附近回绕;位图所有 32 位的查找结果;缓冲满/空/回绕 |
| 调度场景测试 | 脚本化任务 + 虚拟时间,断言派发序列 | 高优先级事件在当前单步后立即派发;`again_limit = N` 时低优先级任务每 N 步获得一次机会;只剩让出任务时不进入等待 |
| 随机状态机测试 | 固定种子的随机操作序列,每步检查不变量(`test/test_random.c`) | 调度器:事件/停止/重启/闹钟/随机返回值/时间推进,跨回绕;不变量含"匹配事件 ⇒ 就绪""到达的释放或闹钟 ⇒ 就绪或扫描待执行"。环形缓冲:对照参考队列模型。变异验证:`next_due` 缓存的一个缺陷只有这里能发现 |
| 并发测试 | 主机平台用真实线程模拟异步上下文 | 生产者线程高频写缓冲,消费者不丢数据、不重复;任务运行中到达的事件不丢失 |
| 监控测试 | 超预算、饿死、错误返回 | 心跳饿死 → 健康信号停止;重启超限 → 安全停机 |
| 生成器测试 | 合法/非法描述文件 | 每条构建期检查至少一个反例;相同输入逐字节相同输出 |
| 契约一致性测试 | 与平台无关,在每个平台适配上运行(`platform/contract_tests/`) | 见下 |

**契约一致性套件(v0.4)** 只调用 7 个契约函数,不依赖内核。平台适配提供一个很小的测试桩(`sos_ct_setup`、`sos_ct_let_time_pass`、可选的异步上下文、输出函数),然后调用 `sos_contract_run()`:

| 检查 | 内容 |
|---|---|
| constants | 计数宽度与 `sos_tick_t` 一致,速率 > 0 |
| time: monotonic / progress | 20 万次读取不倒退(虚拟平台上每项都从回绕点前开始);时间至少按桩推进的量前进 |
| critical: nesting / excludes async | 可嵌套;持有期间异步上下文确实无法进入;异步上下文自身也能(嵌套)进入 |
| wait: reaches deadline / past deadline | 允许提前返回但最终到达截止时刻;过去的截止时刻立即返回 |
| notify: sticky / async ends wait | 等待前的通知让下一次等待立即返回;异步通知结束进行中的等待 |
| health: non-blocking | 健康信号不阻塞 |

`sos_platform_halt` 不返回,无法通用测试,需在目标上人工验证(例如确认看门狗复位)。套件本身做过变异验证:人为去掉通知的粘滞性、把互斥区改为空操作,对应检查都会失败。

## 3. 独立成库(D6)

### 3.1 仓库内容

```
smartOs/                          独立仓库
├── kernel/                       内核源码(唯一被链接进产品的部分)
├── platform/
│   ├── sos_platform.h            契约
│   ├── host/                     虚拟时间平台 + 线程平台(测试用)
│   └── contract_tests/           契约一致性测试
├── tools/sosgen/                 配置生成器源码(Python 3.11+,无第三方依赖,D9)
├── examples/                     最小示例、流水线示例、手写配置示例
├── test/                         单元、场景、并发、生成器测试
├── docs/                         本设计文档
├── CHANGELOG.md
└── LICENSE                       MPL-2.0 全文(D7)
```

具体平台的适配**不放在本仓库**,由使用方在自己的项目中实现(可参考附录 A)。这样内核仓库始终保持零平台依赖。

### 3.2 许可证:MPL-2.0(D7)

MPL-2.0 是**文件级**弱著作权许可:修改 smartOs 自身的文件必须以 MPL-2.0 公开这些修改,但与之链接的其他文件可以采用任何许可(包括闭源)。对使用方的含义:

| 文件 | 归属 | 是否需要公开 |
|---|---|---|
| `kernel/`、`platform/sos_platform.h`、`tools/sosgen/` 中的原有文件 | smartOs | 原样使用无需公开;**修改后**须以 MPL-2.0 提供修改后的这些文件 |
| 使用方的任务代码、平台适配 | 使用方 | 否,可闭源 |
| 使用方的描述文件 | 使用方 | 否 |
| `sosgen` 生成的 `sos_cfg_gen.*`、`sos_cfg.h` | 使用方 | 否(见下) |

落实措施:

1. 每个 smartOs 源文件头部放 MPL-2.0 附件 A 规定的标准声明。
2. 生成器输出的文件头部写明"本文件由 sosgen 生成,属于使用方的配置,不受 MPL-2.0 约束",并在 README 与 `tools/sosgen/` 中同样声明。生成器的模板只产生数据表和声明,不嵌入内核实现代码,使这一声明站得住。
3. 不引入任何与 MPL-2.0 不兼容的第三方代码;生成器只用 Python 标准库,天然满足。
4. 若产品对许可有特殊要求,以法务审核为准;本节只是工程层面的约定。

### 3.3 集成方式

- **构建系统中立**:内核是一组 `.c` 文件加一个头文件目录,没有内部构建逻辑。仓库提供一份文件清单和一个 CMake 目标作为便利,但不强制。
- **使用方提供三样东西**:平台适配(实现契约)、描述文件(生成配置)、任务代码。
- **引入方式**:源码拷贝、git 子模块或包管理器均可;推荐子模块并锁定版本标签。
- **生成器的使用(D9)**:第一阶段只以源码形式随仓库提供,不打包、不发布到包仓库。使用方在构建中以 `python3 <smartOs>/tools/sosgen` 的方式调用;生成器版本即仓库版本标签,与内核天然一致。等接口稳定(v1.0 之后)再评估是否打包为独立命令行工具。

### 3.4 版本规则

| 变化 | 版本号 |
|---|---|
| 公共 API、平台契约或配置 ABI 不兼容变更 | 主版本 +1 |
| 新增兼容功能(如新的可选入口、新钩子) | 次版本 +1 |
| 缺陷修复 | 修订号 +1 |

配置 ABI 版本单独编号并写入配置根,`sos_init` 校验,防止新内核配旧生成结果。
