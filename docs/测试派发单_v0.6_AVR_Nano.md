## 1. 背景(给不熟悉 smartOs 的执行者)

smartOs 是协作式、运行到完成的调度核心:任务的 `run` 每次推进一步就返回(`OK` / `AGAIN` / `STOP` / `ERR`),内核用就绪位图选最高优先级任务,一次只派发一步。异步上下文(中断)只能调用 `sos_event_set_async` 和环形缓冲的生产者接口。必读:

- `docs/03_调度核心设计.md`(调度、让出、监控、错误策略)
- `docs/04_接口规格.md` 第 10 节(哪些接口可在中断里调用)
- `platform/avr_nano/README.md`(本平台的实现与已知注意事项)

平台要点:时间源为 Timer1(clk/64 = 250 kHz,4 µs/tick,32 位,约 4.77 h 回绕一次);互斥区 = 保存 SREG + `cli`;空闲时 IDLE 睡眠,由 OCR1A 或任何中断唤醒;健康信号 = `wdt_reset()`。**Timer1 归平台使用,测试只能用 Timer2(以及 Timer0,如需要)。**

约束:

1. **不修改 smartOs 的任何文件**。需要不同内核参数时,通过测试项目自己的 `sos_cfg.h` 或 `-D` 设置。

## 3. 测试用例

### T1 等待与通知的竞态(清单第 3 项)

**目的**:中断恰好落在"内核判定空闲"与"进入睡眠"之间时,事件不会被拖到下一个唤醒点。

**方法**

1. 配置:1 个事件任务 `E`(优先级 0),无周期任务;`SOS_CFG_HEALTH_MIN_INTERVAL` 设为 250 ms 或关闭监控(`SOS_CFG_SUPERVISE_ENABLE 0`),使空闲时的下一次自然唤醒很远(≥ 245 ms)。
2. Timer2 CTC 中断:每次中断记录 `stamp = sos_time_now()`,再 `sos_event_set_async(E, 1)`。`E` 的 `run` 计算 `latency = now − stamp`,记录最大值与直方图(< 50 µs、< 200 µs、< 1 ms、≥ 1 ms),然后**设置一个标志允许下一次中断**(握手,避免事件合并)。
3. 每次中断后把 OCR2A 改成下一个值(1…255 循环扫描,预分频 8 与 64 各跑一轮),让中断相位扫过调度循环的每个位置。
4. 共 100 000 次事件。

**通过标准**:所有事件都被处理;`latency` 最大值 < 1 ms;**没有任何一次 ≥ 200 ms**(那意味着唤醒丢失,事件等到了下一次自然唤醒)。

**附加(建议)**:在测试项目里复制一份 `avr_platform.c`,把 `wait_until` 开头的粘滞检查删掉,重跑 T1,确认测试能抓到(应出现 ≥ 200 ms 的延迟)。这份副本只用于验证测试本身,不提交回 smartOs。

**记录**:最大延迟、直方图、事件总数、预分频/扫描范围。

### T2 高频事件与环形缓冲不丢数据(清单第 4 项)

**目的**:中断以高频率写入环形缓冲,任务运行期间到达的数据既不丢失也不重复。

**方法**

1. 配置:`SOS_CFG_RING_ENABLE 1`;一个环形缓冲 `rx`(元素 `uint16_t`,容量 32,生产者 = 异步上下文 `SOS_TASK_NONE`,消费者 = 任务 `C`,`notify` 绑定 `C` 的事件)。
2. Timer2 中断以 1 kHz、5 kHz、10 kHz 三档写入递增序号 `sos_ring_put(rx, &seq)`;`FULL` 时计数但不重试。
3. 消费者 `C` 每步最多取 8 个,检查序号连续(允许的缺口只能来自已计数的 `FULL`);仍有数据则返回 `AGAIN`。
4. 另加一个低优先级周期任务 `B`(10 ms),每步忙等 0.5 ms,制造"任务运行中有中断到达"的情况。
5. 每档运行 10 分钟。

**通过标准**:`收到的个数 + FULL 次数 = 写入次数`;没有重复、没有未计数的缺口;`sos_ring_get_stats` 的 `overflow_cnt` 与中断里计数的 `FULL` 次数一致(上限 65535 饱和)。记录每档是否出现 `FULL`,以及 `high_water`。

### T3 各模块组合的代码与 RAM(清单第 5 项)

**方法**:用同一个最小应用(1 个周期任务 + 1 个事件任务,平台适配,不打印),分别以下列参数构建,记录 `avr-size` 的 text / data / bss:

| 组合 | 参数 |
|---|---|
| full | 默认(`RING 1`,`ZERO_COPY 1`,`SUPERVISE 1`) |
| nozc | `SOS_CFG_RING_ZERO_COPY 0` |
| noring | `SOS_CFG_RING_ENABLE 0` |
| nosup | `SOS_CFG_SUPERVISE_ENABLE 0` |
| minimal | `SOS_CFG_RING_ENABLE 0`、`SOS_CFG_SUPERVISE_ENABLE 0` |

另外对每个组合单独编译 smartOs 内核的 7 个 `.c`(`-Os -mmcu=atmega328p -ffunction-sections`),给出**仅内核**的 text 合计,以及 `sizeof(sos_kernel_t)` 等运行时 RAM(可用 `avr-nm --size-sort` 查 `sos_k`)。`SOS_CFG_MAX_TASKS` 分别取 4 和 8 各一组。

**记录**:两张表(整机固件 / 仅内核),注明编译器版本与优化选项。

### T4 执行开销(清单第 6 项;产出 `dispatch_overhead`)

**方法**:在被测路径前后翻转一个空闲 GPIO(如 D8/PB0,`PINB = _BV(PB0)` 一条指令),用逻辑分析仪测脉宽;每条路径至少采 10 000 次,记录**最小 / 平均 / 最大**。测量期间关闭串口输出。

| 编号 | 路径 | 测法 |
|---|---|---|
| T4.1 | 派发开销:`sos_poll` 选出一个就绪任务并调用其空 `run`(直接返回 `AGAIN`) | `sos_poll` 前后翻转;再减去空 `run` 内翻转得到的部分。任务数 1、4、8 各测一次 |
| T4.2 | 周期释放扫描:N 个周期任务同时到期 | N = 1、4、8 |
| T4.3 | `sos_event_set`(任务中)与 `sos_event_set_async`(Timer2 中断中) | |
| T4.4 | 中断到任务开始的唤醒延迟:中断里翻转一次,任务 `run` 第一条语句再翻转 | 分空闲睡眠中 / 内核忙时两种 |
| T4.5 | 环形缓冲:`put` / `get`(元素 2、16 字节),`reserve`+`commit`,`acquire`+`release` | |
| T4.6 | 监控检查一次(`HEALTH_MIN_INTERVAL` 到期时),N = 4、8 个任务,含存活窗口 | |
| T4.7 | `sos_time_to_ticks`、`sos_task_set_alarm`(含 64 位运算) | |

**通过标准**:无;这是测量项。

**产出**:

1. 一张表:每条路径的最小 / 平均 / 最大(µs 与 CPU 周期,1 µs = 16 周期)。
2. **推荐的 `dispatch_overhead`**:取 T4.1 在 8 个任务时的**最大值**,向上取整到 4 µs 的倍数,并给出余量的依据。
3. 用推荐值重新运行 `python3 tools/sosgen examples/layered_pipeline/app.toml ... `(在 `[kernel]` 中加 `dispatch_overhead`)附上报告的 schedulability 部分,说明结论是否变化。

### T5 故障恢复(清单第 7 项)

每个子项单独构建一个固件。每次复位后,固件启动时打印 `avr_reset_cause()`(MCUSR:bit3 = WDRF 看门狗、bit0 = PORF 上电)。

| 编号 | 注入 | 期望 |
|---|---|---|
| T5.1 | 任务每次返回 `ERR`,策略 `RESTART`,`max_restart = 3` | `init` 共 4 次 → `SOS_E_RESTART_LIMIT` → 串口打印 `smartOs HALT 0x00000009` → 约 15 ms 后看门狗复位 → 重启后 MCUSR 含 WDRF |
| T5.2 | 任务在某一步里死循环(永不返回) | 健康信号停止 → 约 2 s 后看门狗复位 → WDRF;记录从卡死到复位的实测时间 |
| T5.3 | 高优先级任务持续返回 `AGAIN`(无 `again_limit`),饿死设置了 `alive_window = 1 s` 的心跳任务,心跳的策略为 `IGNORE` | 存活失效 → 健康信号停止 → 看门狗复位;记录时间 |
| T5.4 | 同 T5.3,但心跳策略为 `RESTART` | 心跳被重启(记录次数),超过 `max_restart` 后 `FATAL` → 复位 |
| T5.5 | 环形缓冲生产者任务在 `reserve` 之后返回 `ERR`(策略 `RESTART`) | 重启后 `put` 正常;消费者从未收到那个未提交的槽 |
| T5.6 | 连续 20 次断电重启与 20 次看门狗复位 | 每次都正常启动;**不出现复位循环**(克隆板旧 bootloader 的已知风险,见平台 README) |

**通过标准**:每项都符合"期望"列;任何一次与期望不符都记录完整串口输出。

### T6 长时间压力运行(清单第 7 项)

**方法**:组合 T2(5 kHz)与 T1(扫描中断相位)的负载,再加 2 个周期任务(50 ms、1 s),开看门狗,连续运行 **≥ 24 小时**。每 10 分钟打印一行:运行时间、各任务 `miss_cnt` / `max_step` / `max_job_steps`、环形缓冲 `overflow_cnt` / `high_water`、`sos_error_count()`、T1 的最大延迟。

**重点**:32 位 tick 每约 4.77 h 回绕一次,24 h 会跨越约 5 次回绕——这是回绕安全(证据表 G4)在实物板上的验证。请在报告中标出每次回绕的时刻(tick 从接近 0xFFFFFFFF 变到接近 0),并确认前后各项统计没有异常跳变。

**通过标准**:无看门狗复位;`sos_error_count() == 0`;周期任务 `miss_cnt` 保持 0(或给出原因);T1 最大延迟始终 < 1 ms;跨越回绕前后行为一致。
