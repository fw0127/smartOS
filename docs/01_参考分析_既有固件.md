# 01 参考分析:从既有固件提炼抽象模式

> 本篇是**溯源文档**,会提到原固件的具体硬件和协议,目的是说明 smartOs 的每个抽象从哪里来。
> 后续设计文档(02–05)不依赖本篇中的任何硬件细节。

## 1. 原固件的执行模型

参考对象是一个既有的嵌入式固件,本身没有 OS,但有一套隐式的调度结构:

```
上电
  ├─ 平台准备(栈、上下文区、看门狗解锁/加锁)
  ├─ 模块 A 初始化  ── 失败 → 死循环等复位
  ├─ 模块 B 初始化  ── 失败 → 死循环等复位
  ├─ 模块 C 初始化  ── 失败 → 死循环等复位
  └─ do {
         模块 C.Handler()              ← 上层:按请求类型分发处理
            ├─ 模块 B.Handler()        ← 中层:状态机推进一步
            └─ 取得 B 的完整数据 → 处理
     } while (返回 OK);
     模块 C.Done();  死循环等复位
```

(A/B/C 是原固件中的三个功能层,它们的具体内容对抽象不重要。)

## 2. 从中提炼出的抽象模式

| # | 原固件中的具体做法 | 抽象出的通用模式 | smartOs 中的落点 |
|---|---|---|---|
| 1 | 单一循环反复调用 Handler | **协作式运行到完成** | 调度主循环 |
| 2 | Handler 用 `switch(state)` 每次推进一步就返回 | **任务 = 非阻塞的步进函数** | 任务的 `run` 回调 |
| 3 | 每个模块都有 `Init / Handler / Done` | **统一生命周期** | 任务的 `init / run / done` |
| 4 | 读取自由运行计数器,用 `now − start ≥ limit` 判超时 | **回绕安全的单调时间比较** | 抽象时间模块 |
| 5 | 模块状态放在独立的 locals 结构体中 | **状态与代码分离** | 任务的 `ctx` 指针 |
| 6 | 下层出错时上层执行 `Done + Init` | **局部软恢复** | 错误策略 `RESTART` |
| 7 | 初始化失败进入死循环,等外部复位 | **统一的安全终止** | `sos_fatal` → 平台安全停机 |
| 8 | 查找表以哨兵项结尾 | **表驱动的静态配置** | 静态任务表 |
| 9 | 公共头 / 私有头 / 参数头分离 | **接口分层** | `_pub / _pri / _cfg` |

## 3. 原固件中需要克服的问题

| 问题 | 抽象层面的根因 | smartOs 的处理 |
|---|---|---|
| 调度关系写死在调用链里 | 调度策略与业务逻辑耦合 | 调度策略只存在于内核,任务之间不互相调用 |
| 只有"每轮都跑" | 缺少触发条件与优先级的概念 | 周期 / 事件 / 后台三类触发 + 静态优先级 |
| 每次运行时查表取状态 | 绑定发生在运行期 | 编译期绑定 `ctx`,启动时一次性校验 |
| 无执行时间监控 | 缺少运行时观测 | 每步计时,超预算记录 |
| 看门狗与任务健康无关 | 健康信号没有语义 | 健康信号由存活监控结果决定 |
| 死循环散落各处 | 安全状态没有统一入口 | 唯一入口 `sos_fatal` |
| 寄存器操作混在主模块里 | 缺少平台抽象边界 | 所有平台相关内容收敛到平台契约 |

## 4. 结论

原固件已经是一个手写的协作式调度器,只是调度策略分散在各模块的调用链中。
smartOs 把这套模式抽象出来:**业务写法不变(非阻塞步进函数),调度策略集中到内核,硬件依赖收敛到契约。**
